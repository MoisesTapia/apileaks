# APILeak v1.0.0 — Análisis de Brechas hacia un Framework Completo de Pentesting de APIs

**Fecha:** 2026-11-02
**Rama:** `v1.0.0` (creada desde `main` @ `9d6e496`, que ya incluye el merge de `v1.0.0` / PR #9)
**Alcance:** evaluar qué le falta a APILeak para ser un framework **completo** de pentesting de APIs con:
1. Auditoría credenciada de API Gateways (AWS API Gateway y competidores: Kong, Apigee, Azure APIM, GCP API Gateway).
2. Integración con MCP (Model Context Protocol) e IA.
3. Capacidad de Red Teaming y Blue Teaming.

Este documento es el resultado de (a) un inventario exhaustivo del código actual y (b) investigación externa sobre el estado del arte en plataformas de seguridad de APIs (Salt Security, Akto, Traceable, Noname/Akamai), herramientas de red-teaming de IA/MCP, y guías de seguridad de AWS API Gateway / Kong.

---

## 1. Resumen ejecutivo

APILeak es hoy una **herramienta de pentesting ofensivo de APIs de caja gris/negra, muy madura en explotación real de los 10 módulos OWASP API Security Top 10** (BOLA y Broken Auth en particular hacen explotación real — escalación de privilegios, fuerza bruta, bypass de JWT — no solo detección heurística), con buena cobertura de descubrimiento, fuzzing, WAF/evasion, spec-driven testing (OpenAPI/Postman) e importación de capturas (Burp/HAR). Tiene un gate de CI maduro (ruff + mypy + pytest, ~2380 tests) y soporte de integración en pipelines (SARIF, umbrales, AWS Security Hub como *publicador* de hallazgos).

**Lo que NO tiene, y que es indispensable para llamarse "framework completo":**

- **Cero integración con gateways de nube.** No audita AWS API Gateway, Kong, Apigee, Azure APIM ni GCP API Gateway usando sus credenciales/APIs de administración — solo puede *tropezar* con un proxy Apigee vía wordlist de descubrimiento. Esta es la brecha más grande y la que el usuario pidió explícitamente.
- **Cero integración con MCP.** No existe servidor MCP, cliente MCP, ni ningún código relacionado con IA/LLM/agentes en todo el repositorio.
- **Cero capacidad de Blue Team.** Es una herramienta 100% ofensiva. No genera reglas de detección, no monitorea tráfico en runtime, no tiene modo de "defensa", no integra con SIEM/WAF para *proteger* en vez de solo *atacar*.
- **Red Teaming real (no solo "pentesting automatizado") requiere encadenamiento de ataques multi-paso, generación de PoC/exploit reproducible, simulación de actor de amenaza con objetivos, y estas capacidades existen hoy solo de forma parcial** (BOLA sí encadena pasos; el resto de módulos son independientes entre sí).
- Brechas adicionales de protocolo (GraphQL/gRPC/WebSocket nativos), autenticación (OAuth2 handshake, mTLS, SigV4), y reporting/compliance (sin mapeo a PCI-DSS/SOC2, sin integración con Jira/ticketing).

## 3. Brechas por categoría

### A. Auditoría credenciada de API Gateways (la petición explícita del usuario)

Hoy APILeak solo prueba el *comportamiento HTTP expuesto* de una API. No existe ningún código que, dadas credenciales de administración, lea la **configuración** del gateway que la expone — que es donde viven la mayoría de las misconfiguraciones reales (políticas de recursos abiertas, autorizadores ausentes, throttling mal puesto, WAF no asociado, API keys sin uso-plan, CORS a nivel de gateway, etc.).

| Gap | Por qué importa | Propuesta |
|---|---|---|
| **AWS API Gateway (REST/HTTP/WebSocket APIs)** | Sin boto3 `apigateway`/`apigatewayv2`, no se puede verificar: políticas de recursos (`get_rest_api` → `policy`), si hay autorizador (`get_authorizers`) o la API quedó en modo `NONE`, asociación de AWS WAF WebACL, logging de acceso/ejecución habilitado, si el *stage* usa TLS mínimo correcto, usage plans sin throttle, API keys huérfanas, CORS en nivel de método | Nuevo paquete `modules/cloud/aws_api_gateway.py` + `utils/cloud/aws_client.py` (boto3 `apigateway`, `apigatewayv2`, `wafv2`, `iam` para resolver roles de integración Lambda). Nueva `AuthType.AWS_SIGV4` para firmar requests salientes con SigV4 cuando el API Gateway usa autorización IAM. |
| **Kong (OSS / Enterprise)** | Sin cliente de la Admin API, no se detectan: Admin API expuesta sin autenticación (el hallazgo #1 de todas las guías de Kong), plugins de auth faltantes en una ruta, ACL/rate-limiting-advanced mal configurado, servicios/rutas sin plugin `key-auth`/`jwt`/`oauth2`, CVEs conocidos de versión de Kong | Nuevo `modules/cloud/kong_gateway.py` + `utils/cloud/kong_client.py` (REST contra `/services`, `/routes`, `/plugins`, `/consumers`). Chequeo específico "Admin API alcanzable sin credencial" como finding `CRITICAL`. |
| **Apigee (Google Cloud / Apigee Edge)** | Sin cliente de Apigee Management API: proxies con `VerifyAPIKey`/`OAuthV2` ausente, políticas de quota/spike-arrest, target endpoints con TLS deshabilitado | Nuevo `modules/cloud/apigee.py` |
| **Azure API Management (APIM)** | Sin cliente Azure SDK: políticas XML de APIM, product/subscription sin requerir key, backend sin mTLS, CORS global permisivo | Nuevo `modules/cloud/azure_apim.py` |
| **GCP API Gateway / Cloud Endpoints** | Sin cliente GCP: config de gateway sin `x-google-backend` auth, API sin `securityDefinitions` enforced | Nuevo `modules/cloud/gcp_api_gateway.py` |
| **Modelo de config unificado** | Cada proveedor expone conceptos distintos (resource policy vs. plugin vs. policy XML) que deben normalizarse a los mismos `Finding`/`owasp_category` que usa el resto del motor | Nueva capa de abstracción `CloudGatewayAuditor` (ABC) análoga a `OWASPModule`, con un `GatewayFinding` que se traduce a `Finding` estándar; nuevo comando `apileaks cloud-audit --provider aws --profile prod` |
| **Gestión de credenciales de nube** | Las credenciales de AWS/Kong/Apigee/Azure/GCP no pueden vivir en texto plano en YAML | Soporte de credential chain nativo de cada SDK (boto3 default chain, Azure `DefaultAzureCredential`) + opción de leer secretos desde AWS Secrets Manager / HashiCorp Vault (`utils/cloud/secrets_resolver.py`) |

**Prioridad:** P0 — es el requisito explícito del usuario y el gap más grande frente a competidores (Salt/Akto/Traceable todos tienen "posture management" de gateways nativo).

### B. Integración con MCP (Model Context Protocol)

Hoy cero. Para que "la IA" pueda operar APILeak (o para que APILeak pueda auditar servidores MCP de terceros como superficie de ataque), hacen falta **dos direcciones** distintas:

| Gap | Descripción | Propuesta |
|---|---|---|
| **APILeak como servidor MCP** | Exponer las capacidades de la herramienta (scan, owasp <módulo>, jwt attack-test, discovery, cloud-audit) como *tools* MCP invocables por un agente de IA (Claude, Kiro, etc.), con esquema de entrada/salida tipado y streaming de progreso | Nuevo paquete `mcp_server/` con un server MCP (stdio o HTTP) que envuelve `core/engine.py`/`core/orchestrator.py`; cada comando CLI existente se expone 1:1 como tool MCP (reutilizando `cli/module_options.py` para los esquemas de parámetros) |
| **Auditoría de servidores MCP como objetivo** | Los MCP servers de terceros son ahora superficie de ataque (tool-poisoning, prompt injection vía resultados de tool, confused-deputy, exfiltración de datos vía tool chaining) — ver investigación 2026 (arXiv 2608.00150, 2508.12538) | Nuevo `modules/mcp_security/` con pruebas específicas: enumeración de tools/resources expuestos, tool-description injection, verificación de que el server no ejecuta tools destructivos sin confirmación, fuga de credenciales en logs de tool calls, SSRF vía tool que acepta URLs |
| **Agente orquestador IA-nativo** | Que un LLM pueda planear una campaña de pentesting (elegir qué módulos correr, interpretar resultados, decidir el siguiente paso) en lugar de que el operador invoque módulos manualmente uno por uno | Nuevo `core/ai_agent/` con un loop ReAct simple: LLM recibe el `Finding` acumulado + catálogo de tools MCP, decide próxima acción; requiere API key de proveedor LLM (Anthropic/OpenAI/Bedrock) configurable, con *human-in-the-loop* obligatorio para acciones destructivas (reutilizando `SafeModeGuard`) |
| **Generación de hallazgos asistida por IA** | Usar un LLM para redactar remediación contextualizada, triage/priorización de hallazgos por explotabilidad real, deduplicación semántica de findings similares entre módulos | Nuevo `utils/ai_triage.py`: post-procesa la lista de `Finding` de un scan con un LLM antes del reporte final |

**Prioridad:** P0 para "exponer como MCP server" (es lo que pidió el usuario, y es relativamente acotado); P1 para "auditar MCP servers de terceros" (mercado emergente, alto valor diferenciador); P2 para el agente orquestador autónomo (mayor riesgo/complejidad, requiere guardrails serios).

### C. Red Teaming

Red teaming real (no solo "vulnerability scanning automatizado") implica: actuar como un adversario con un **objetivo** (ej. "exfiltrar PII de otro tenant"), encadenar **múltiples técnicas de múltiples módulos OWASP** en una sola cadena de ataque, y producir una **prueba de concepto reproducible** paso a paso — no solo una lista plana de findings.

| Gap | Descripción | Propuesta |
|---|---|---|
| **Encadenamiento de ataques entre módulos** | Hoy cada módulo OWASP corre independiente; BOLA internamente encadena pasos (`_test_chained_state_manipulation`) pero no hay encadenamiento *entre* BOLA→Auth→SSRF, por ejemplo "robar JWT vía SSRF al endpoint de metadata → usar ese JWT para escalar en BOLA" | Nuevo `core/attack_chains.py`: motor de grafo de ataque donde la salida (`Finding`/`EvidenceChain`) de un módulo puede alimentar la entrada de otro; definir "kill chains" predefinidas (ej. `ssrf_to_credential_theft_to_bola`) |
| **Perfiles de actor de amenaza** | Simular un atacante con objetivo y presupuesto de tiempo/ruido (ej. "insider malicioso con cuenta de bajo privilegio" vs. "atacante externo anónimo") | Nuevo `core/threat_actor.py`: perfiles que restringen qué `AuthContext`/técnicas están disponibles y en qué orden se intentan, emulando TTPs de MITRE ATT&CK (mapeado parcial ya existe para API vía OWASP, falta el mapeo explícito a ATT&CK) |
| **Generación de PoC reproducible** | Un hallazgo hoy es evidencia textual (`evidence` string); un red team necesita un script/curl reproducible paso a paso para el reporte ejecutivo | Extender `Finding` con `reproduction_steps: list[HttpStep]` y un generador de PoC (`utils/poc_generator.py`) que emite un script Python/curl mínimo por cada finding crítico |
| **Operaciones de larga duración / C2-like persistence testing** | Nada en el repo prueba persistencia de sesión robada en el tiempo, rotación de tokens, o mantenimiento de acceso tras remediación parcial | Fuera de alcance de una herramienta de API (esto es más dominio de C2 de red/host); se puede limitar a "token replay después de rotación" ya cubierto parcialmente por `auth_testing.py` (logout/expiration) |

**Prioridad:** P1 — el encadenamiento de ataques y los perfiles de actor son el diferenciador real de "red team" vs. "scanner"; la generación de PoC es de impacto inmediato para reportes ejecutivos.

### D. Blue Teaming (ausente por completo)

APILeak es puramente ofensivo. Un framework que se anuncie como "capacidad de blue teaming" necesita el lado defensivo: detectar lo que el red team hizo, generar reglas, y verificar que la defensa funciona.

| Gap | Descripción | Propuesta |
|---|---|---|
| **Generación de reglas de detección** | Ningún módulo produce una regla WAF/SIEM a partir de un ataque exitoso | Nuevo `utils/detection_rule_generator.py`: por cada `Finding` explotado con éxito, emitir una regla AWS WAF (JSON), una regla Kong (plugin config), y una query Sigma/SIEM genérica que detectaría el mismo patrón de petición |
| **Modo "purple team" (verificación de detección)** | Tras generar una regla, no hay forma de re-emitir el mismo ataque y verificar si la regla/WAF ahora lo bloquea | Nuevo flag `apileaks owasp bola --verify-detection` que repite el ataque exitoso y confirma `403`/bloqueo tras aplicar la mitigación sugerida |
| **Monitoreo de tráfico en runtime / detección de anomalías en producción** | No existe ningún componente pasivo que observe tráfico real (vs. generarlo activamente) | Nuevo `modules/blue_team/traffic_monitor.py`: consumidor opcional de logs de acceso (CloudWatch/Kong logs/APIM diagnostics) que aplica los mismos detectores de anomalía que ya existen para BOLA/auth (IDOR secuencial, reutilización de token) pero en modo pasivo/continuo |
| **Integración con SIEM/alerting** | Sin salida hacia Splunk/Elastic/Sentinel, sin webhooks a Slack/PagerDuty en tiempo real durante un scan | Nuevo `utils/alerting.py` con sinks configurables (webhook genérico, Slack, PagerDuty, Elastic Common Schema) |
| **Baseline de postura y drift** | `utils/baseline.py` ya compara hallazgos entre dos scans — se puede extender para comparar **configuración de gateway** entre dos auditorías (requiere el módulo A primero) | Extender `baseline.py` para incluir diffs de `GatewayFinding` (ver sección A) |

**Prioridad:** P1 para generación de reglas y modo purple-team (alto valor con esfuerzo moderado, reutiliza infraestructura existente); P2 para monitoreo continuo/SIEM (es, en esencia, un producto nuevo de runtime protection, no una feature incremental).

### E. Autenticación y gestión de credenciales (al objetivo bajo prueba)

| Gap | Descripción | Propuesta |
|---|---|---|
| Sin handshake OAuth2/OIDC real | `AuthType` solo tiene `BEARER/BASIC/API_KEY/JWT`; no hay `client_credentials`/`authorization_code`/`password` grant automatizado | Nuevo `AuthType.OAUTH2` + `utils/oauth_flow.py` que obtiene y refresca tokens automáticamente durante el scan |
| Sin mTLS | Ningún soporte de certificado cliente en `utils/http_client.py` | Añadir `client_cert`/`client_key` a `AuthContext` y propagarlo al cliente HTTP (httpx ya soporta esto nativamente — es solo wiring) |
| Sin AWS SigV4 | Necesario para API Gateway con autorización IAM | Ver sección A — `AuthType.AWS_SIGV4` |
| Sin integración con vaults de secretos | Tokens/credenciales viven en YAML plano | `utils/cloud/secrets_resolver.py` (AWS Secrets Manager, HashiCorp Vault, Azure Key Vault) referenciable desde `core/config.py` vía `${vault:path}` |

**Prioridad:** P1 (OAuth2 y mTLS son básicos para auditar APIs empresariales reales).

### F. Cobertura de protocolos

| Gap | Descripción |
|---|---|
| **GraphQL** | Sin introspección de schema, sin batching-attack, sin field-suggestion-based enumeration, sin alias-based rate-limit bypass — hoy `resource_consumption.py` tiene un chequeo genérico de "complex queries" pero no hay módulo GraphQL dedicado |
| **gRPC** | Sin soporte de protobuf/reflection; APIs internas modernas cada vez más usan gRPC |
| **WebSocket** | Sin pruebas de autenticación/autorización en mensajes WS post-handshake |
| **SOAP/XML legacy** | `defusedxml` ya está en el repo (anti-XXE) pero no hay módulo que pruebe XXE/XML-bomb activamente contra un endpoint SOAP |
| **Async/event-driven (webhooks, Kafka, AsyncAPI)** | Sin soporte de AsyncAPI spec ni pruebas de validación de firma de webhook |

**Prioridad:** P1 para GraphQL (altísima adopción), P2 para el resto.

### G. Reporting, compliance y gestión de hallazgos

| Gap | Descripción |
|---|---|
| Sin mapeo a frameworks de compliance | No hay traducción de `Finding.owasp_category` a controles PCI-DSS / SOC2 / ISO 27001 — competidores (Salt, Akto) lo anuncian como feature clave |
| Sin integración de ticketing | No hay creación automática de issues en Jira/GitHub Issues/Linear desde hallazgos críticos |
| Sin PDF/CSV en el generador principal | `utils/report_generator.py` no genera PDF ni CSV (sí existe generación de PDF en el script CI-separado `ci-cd/scripts/report_generator.py`, pero no en el flujo principal del CLI) |
| Sin tracking histórico/tendencias | `utils/baseline.py` compara dos scans puntuales; no hay serie de tiempo ni dashboard de tendencia de riesgo |

**Prioridad:** P2 (importante para venta/adopción enterprise, pero no bloquea la función core de pentesting).

### H. Arquitectura y escalabilidad

| Gap | Descripción |
|---|---|
| Sin modo distribuido/paralelo multi-host | Todo corre en un solo proceso; no hay orquestación de múltiples targets en paralelo a escala (ej. auditar 500 APIs de un portafolio) |
| Sin API REST propia para controlar la herramienta remotamente | Solo CLI; no hay servidor HTTP que permita lanzar/consultar scans programáticamente (esto también es prerequisito natural para el servidor MCP de la sección B) |
| Sin modo multi-tenant/SaaS | Pensado para ejecución local/CI, no como plataforma compartida |

**Prioridad:** P2, salvo la API REST propia que es P1 porque es compartida con el requisito de MCP (un server MCP necesita básicamente esto mismo por debajo).

### I. Inteligencia de amenazas y correlación

| Gap | Descripción |
|---|---|
| Sin correlación con CVEs conocidos | `framework_detector.py` identifica el framework backend pero no cruza versión detectada contra una base de CVEs (NVD/OSV) |
| Sin SBOM de dependencias de la API bajo prueba | No se intenta inferir/enumerar dependencias del servicio objetivo |

**Prioridad:** P2.

## 5. Riesgos y consideraciones

- **Alcance de credenciales de nube:** cualquier módulo que use boto3/Kong Admin API/Azure SDK/GCP SDK con credenciales reales de producción debe documentarse como *solo lectura por defecto* (ningún cambio de configuración sin `--allow-destructive`), siguiendo el mismo patrón `SafeModeGuard` ya establecido.
- **Guardrails del agente de IA:** cualquier acción destructiva decidida por un LLM debe pasar por confirmación humana explícita; nunca debe poder deshabilitar `SafeModeGuard` por sí mismo.
- **Superficie de ataque nueva al exponer MCP:** un servidor MCP mal asegurado es, literalmente, la vulnerabilidad #1 que la sección B.2 pide auditar en otros — el propio servidor MCP de APILeak debe pasar esa misma auditoría antes de publicarse (dogfooding obligatorio).
- **Tamaño del esfuerzo:** esta lista representa fácilmente 6-12 meses de desarrollo a tiempo completo si se ataca todo; se recomienda secuenciar por las prioridades P0→P1→P2 y validar cada bloque con los ~2380 tests existentes más los nuevos que cada módulo requiera.

## 6. Metodología

Este análisis combina:
1. Inventario exhaustivo del código actual (ver `invoke_sub_agent: context-gatherer`, sesión 2026-11-02) cubriendo los 10 módulos OWASP, módulos avanzados, autenticación, CLI, extensibilidad, spec-driven testing, captura/replay y CI.
2. Búsqueda externa sobre: checklist de seguridad de AWS API Gateway (AWS Whitepaper "Security Overview of Amazon API Gateway", docs de resource policies/usage plans/WAF), seguridad de Kong (Admin API exposure, docs oficiales de Kong), diseño de servidores MCP para pentesting (`pentestMCP`, `pentest-mcp`, papers arXiv 2608.00150 / 2508.12538 sobre superficie de ataque de MCP en producción), y comparación de plataformas comerciales de seguridad de APIs (Salt Security, Akto, Traceable, Noname/Akamai) para calibrar qué se considera "completo" en el mercado 2025-2026.
